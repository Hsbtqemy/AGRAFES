### QA-01 — « ✕ Retirer la borne » est un contrôle mort en Curation et Annotation

- **Sévérité** : 🟠 (fonction inaccessible depuis la couche où l'utilisateur la cherche ;
  contournement existant, pas de perte de données)
- **Repro** : couche **Curation**, doc 416 `Beigbeder-Francs_FR` (`text_start_n=4`) →
  cliquer « ✕ Retirer la borne » sur le marqueur ⚑ → **rien ne se passe**, aucune erreur console.
  Idem couche **Annotation**. Fonctionne en couche **Rôles**.
- **Cause racine** (lue au code) :
  - `CanvasUnitList._textStartMarkerHtml()` (`CanvasUnitList.ts:131`) rend le bouton
    **inconditionnellement** ;
  - le handler (`CanvasUnitList.ts:249-252`) appelle `this._opts.onClearTextStart?.()` —
    **optional chaining ⇒ no-op silencieux** quand l'option est absente ;
  - `onClearTextStart` n'est câblé que dans `RolesPane.ts:147`. `CurationPane.ts:206` et
    `AnnotationPane.ts:124` construisent la liste sans cette option, tout en passant bien
    `textStartN` (`CurationPane.ts:246`, `AnnotationPane.ts:187`) → le marqueur s'affiche,
    le bouton est inerte.
- **Origine** : `725f337` (R5.1a, extraction de `CanvasUnitList` depuis `RolesPane`) — le HTML du
  marqueur a suivi, le callback est resté propre à l'appelant d'origine. Jamais rattrapé : aucun
  test ne couvre le bouton hors Rôles.
- **Contournement** : couche Rôles, même document → le bouton y appelle
  `setDocumentTextStart(conn, docId, null)` (`RolesPane.ts:395-415`).
- **Fix à trancher** :
  - (a) ne rendre le bouton que si `onClearTextStart` est fourni → zéro contrôle mort, le geste
    reste propriété de Rôles (cohérent : on ne peut pas *poser* la borne depuis Curation, ces panes
    n'ont pas de modèle de sélection) ;
  - (b) câbler `onClearTextStart` dans Curation + Annotation → geste transversal (précédent du
    stylo D-C5), mais asymétrique (retrait possible, repose seulement en Rôles).
- **Test à ajouter dans les deux cas** : render-smoke montant le marqueur sans `onClearTextStart`
  et vérifiant l'invariant retenu (bouton absent, ou clic → appel).

### QA-02 — la feuille d'actions du canvas n'est pas peinte (éditeur de token invisible)

> **Diagnostic corrigé en cours de passe.** La première hypothèse — conflit de `z-index` avec le
> rail de nav — était **fausse** : les mesures en console montrent une géométrie correcte. Le
> correctif `z-index: 120` initialement proposé n'aurait rien réglé. Cause réelle ci-dessous.

- **Sévérité** : 🟠 (fonction inaccessible en pratique : l'utilisateur ne voit pas le bouton
  « Enregistrer » et conclut que l'édition de token ne s'enregistre pas ; pas de perte de données)
- **Repro** : couche **Annotation**, document annoté → cliquer un token coloré → l'éditeur s'ouvre
  dans la feuille fixée en bas, mais **la rangée d'actions n'apparaît pas à l'écran**.
  **Deux déclencheurs distincts la font apparaître** (donc deux repaints forcés, pas un accident
  de premier rendu) : redimensionner la fenêtre (agrandir puis revenir à la taille initiale),
  ou changer de panneau / passer par le module Explorer du shell et revenir.
  Le défaut se reproduit à **chaque** ouverture de l'éditeur tant qu'aucun repaint n'est forcé.
- **Mesures (console, éditeur ouvert, fenêtre 1536×842)** — la géométrie était déjà bonne
  *avant* le redimensionnement :
  - boîte de l'éditeur : `x=308 y=646 l=920 h=188` → dans la fenêtre, à droite du rail (48 px) ;
  - bouton « Enregistrer » : **présent dans le DOM**, `x=320 y=804`, donc au-dessus de la ligne
    de flottaison (842) ;
  - `getComputedStyle(.prep-canvas-root).containerType === "inline-size"`.
  → Layout juste, **pixels manquants** : c'est une invalidation de peinture, pas un problème de
  positionnement ni d'empilement.
- **Cause racine** : `.prep-canvas-root { container-type: inline-size }` (`app.css:4959`) applique
  la **containment de layout**, ce qui fait de cet élément (a) le bloc conteneur des descendants
  `position: fixed` et (b) un contexte d'empilement. `.prep-canvas-bottomsheet`
  (`position: fixed`, `app.css:5037`) est un descendant : il devient un *fixed contenu*. Chromium /
  WebView2 rate l'invalidation de peinture de ce sous-arbre quand son contenu change (injection de
  l'éditeur) ; tout repaint forcé (redimensionnement) rétablit l'affichage.
- **Collision de deux lots, aucun des deux fautif isolément** :
  - `817b917` (**R5.3**, 2026-07-03) introduit la feuille `position: fixed` — correcte à l'époque ;
  - `72a4f20` (**R6.4·T4a**, 2026-07-20) ajoute `container-type: inline-size` pour le responsive
    par container query → ré-ancre et contient silencieusement la feuille.
  Ni la purge CSS `aa7ded3` ni le lot de juillet ne sont en cause (diff vérifié).
- **Correctif** : supprimer la combinaison, pas la symptomatique. Deux voies :
  - (a) **sortir la feuille de `.prep-canvas-root`** dans le DOM (la monter au niveau de la racine
    de l'écran / du body) → `position: fixed` redevient relatif au viewport ;
  - (b) **déplacer `container-type`** sur un wrapper interne qui ne contient pas la feuille
    (garde les container queries du canvas).
  ⚠️ Ne PAS se contenter d'un repaint forcé en JS (`offsetHeight`, toggle de classe) : ça masque
  la cause et laisse le piège en place pour la prochaine box logée dans la feuille.
- **Défaut annexe, réel mais distinct** : `.prep-annot-token-editor` (`app.css:5297`, écrit pour un
  montage *dans* la pane) écrase, à spécificité égale mais déclaré plus loin, le contrat du dock —
  `border-radius` (`6px` au lieu de `12px 12px 0 0`) et `margin-bottom` (`0.5rem` au lieu de `0`).
  `.prep-seg-canvas-applybar` (barre de Rôles) ne souffre pas du problème : elle a été écrite *pour*
  le dock (`border-bottom: none`, radius hérité). L'éditeur est re-parenté par
  `AnnotationPane.ts:156` sans adaptation CSS.
- **Test à ajouter** : aucun test unitaire ne couvre une géométrie ni une peinture — c'est
  précisément pourquoi la collision R5.3 × R6.4 est passée. À défaut d'un test de rendu réel,
  poser une **règle d'architecture** (lint ou revue) : aucun `position: fixed` sous un ancêtre
  portant `container-type`/`contain`.

### QA-03 — couche Rôles : on peut retirer un rôle, pas en poser (barre d'actions)

- **Sévérité** : 🟠 (la fonction principale de la couche est non découvrable depuis la surface
  contextuelle ; aggravé par un bouton trompeur)
- **Repro** : couche **Rôles** → cliquer un segment **sans rôle** → la barre d'actions affiche
  `1 unité · ✕ Retirer rôle · ✕ Désélectionner · ⚑ Borne texte`. Deux problèmes :
  1. « ✕ Retirer rôle » est proposé alors que l'unité **n'a aucun rôle** → action sans effet, et
     le bouton laisse croire qu'un rôle est posé ;
  2. **aucun moyen d'assigner** un rôle depuis cette barre.
- **Cause racine** — trois facteurs cumulés, tous dans `RolesPane.ts` :
  1. `_renderActionBar` (`RolesPane.ts:368-373`) émet « Retirer rôle » **inconditionnellement** :
     aucun test de `unit_role` sur les unités sélectionnées ;
  2. le **seul** chemin d'assignation est le clic sur un `.prep-conv-role-item` du **catalogue**
     (`RolesPane.ts:314`), qui vit **en haut de la pane** et est **replié par défaut**
     (`data-open="false"`, `RolesPane.ts:85`) ;
  3. l'en-tête du catalogue s'annonce « **créer / modifier / supprimer** » (`RolesPane.ts:89`) —
     il se présente comme un panneau de *gestion*, pas comme la surface d'*assignation*.
  Le seul indice est `#prep-conv-assign-hint` (« …ouvrir le catalogue et cliquer un rôle pour
  assigner », `RolesPane.ts:361`) — mais il est rendu **en haut** (`RolesPane.ts:123`), donc hors
  écran dès qu'on travaille dans le corps d'un document, au moment précis où il servirait.
- **Le fond du problème** : la feuille d'actions contextuelle (R5.3) a été conçue pour porter les
  gestes de la sélection. Elle porte le **neutre** (désélectionner), le **destructif** (retirer) et
  un geste **de document** (borne texte) — mais pas le geste **principal** de la couche. La
  hiérarchie est inversée.
- **Troisième manque, même surface (constaté en préparant l'item 3.5)** : **aucun bouton d'annulation
  dans la couche Rôles**. `RolesPane.ts` n'en contient aucun ; les deux seuls contrôles undo de Prep
  sont `#prep-cur-undo-btn` (CurationPane) et `#prep-seg-canvas-undo` (SegmentPane). Or le moteur
  enregistre bien l'assignation de rôle comme action annulable Mode A (**migration 033**, livrée
  pour ça en tranche 2 du retrait Segmentation) et le front connaît le type (`set_role`,
  `prepUndo.ts:33`). Conséquence : pour annuler un rôle, il faut basculer sur **une autre couche** —
  dont le bouton s'annonce « Annuler la dernière action (curation appliquée ou édition) »
  (`CurationPane.ts:130`), sans mentionner les rôles. Capacité moteur livrée, non atteignable là où
  le geste se fait.
- **Correctif proposé (front pur, zéro contrat)** :
  - rendre les **puces de rôle assignables dans la barre d'actions** elle-même (ordre `sort_order`,
    clic → `_assignRole(name)`), là où la sélection est signalée ;
  - **conditionner** « Retirer rôle » à la présence d'au moins un `unit_role` dans la sélection
    (masqué ou désactivé sinon) ;
  - **ajouter le bouton d'annulation** à la couche Rôles (`prepUndo` + `prepUndoEligibility`, déjà
    utilisés à l'identique par Curation et Segment — rien à écrire côté moteur) ;
  - une fois l'assignation déplacée, le catalogue redevient ce que son en-tête annonce : de la
    gestion de rôles.
- **Test à ajouter** : render-smoke de `_renderActionBar` — sélection sans rôle ⇒ pas de bouton
  « Retirer rôle » ; sélection avec rôle ⇒ bouton présent ; barre contenant les puces assignables.

### QA-04 — index FTS irréparable après une base « recover » (tables fantômes orphelines)

- **Sévérité** : 🟠 en général, **🔴 pour qui le rencontre** — la recherche est morte sur la base et
  **aucun remède n'existe depuis l'application** (le réindex échoue lui aussi).
- **Constat** : le log du shell crache en boucle
  `stale_doc_ids: FTS query failed (no such table: fts_units)`. Inspection de
  `corpus_agrafes.WORKCOPY.db` : les **5 tables fantômes FTS5** sont présentes
  (`fts_units_config/_content/_data/_docsize/_idx`) mais la **table virtuelle `fts_units` est
  absente**. 46 674 unités `line` sont donc non indexées.
- **Défaut moteur — démontré, pas déduit** (repro minimale sur base jetable) :
  `build_index` (`indexer.py:88-95`) rattrape l'erreur FTS et appelle `_recreate_fts_table`
  (`indexer.py:40-75`), qui commence par `DROP TABLE IF EXISTS fts_units`. Dans cet état la table
  virtuelle **n'existe pas** → le DROP réussit **silencieusement** → la branche de secours qui
  supprime les tables fantômes (`indexer.py:48-54`) **ne se déclenche jamais**, car elle est
  conditionnée à l'échec du DROP. Le `CREATE VIRTUAL TABLE` de la ligne 73 échoue alors :
  ```
  OperationalError: fts5: error creating shadow table fts_units_data: table 'fts_units_data' already exists
  ```
  → **la réparation est impossible par le chemin prévu**, quel que soit le nombre de réindex lancés.
- **Origine probable** : base reconstruite par `sqlite3 .recover` après corruption — les fichiers
  voisins `corpus_agrafes.RECOVERED.db` et `corpus_agrafes.db.CORRUPT-BAK` en témoignent.
  `.recover` réémet les tables fantômes comme **tables ordinaires** mais ne réémet pas le
  `CREATE VIRTUAL TABLE`. **Tout corpus réparé ainsi atterrit dans cet état** : c'est un scénario
  utilisateur réel, pas un artefact de test.
- **Correctif** : supprimer les tables fantômes **inconditionnellement avant** le CREATE (ou
  rattraper l'échec du CREATE et retenter après purge des fantômes). Côté moteur, petit et testable
  — la liste `_FTS5_SHADOW_SUFFIXES` existe déjà (`indexer.py:37`), seule la condition de
  déclenchement est mal placée.
- **Test à ajouter** : construire l'état pathologique (créer la vtable, la retirer de
  `sqlite_master` via `writable_schema`, garder les fantômes) puis vérifier que `build_index`
  reconstruit l'index. RED prouvé sur le code actuel.
- **Effet sur cette passe de QA** : tout ce qui touche la **recherche** était inopérant sur cette base
  (bloc 6.8 Explorer/Recherche, signal « index périmé »). **Sans rapport avec le lot de juillet.**
- **Réparation appliquée (2026-08-17, base de QA uniquement)** — le défaut moteur reste à corriger :
  1. sauvegarde préalable par l'API `backup` de SQLite (copie cohérente malgré le WAL) →
     `corpus_agrafes.WORKCOPY.PRE-FTS-REPAIR.db` (259,2 Mo, `integrity_check: ok`) ;
  2. purge des 5 tables fantômes, puis appel de `indexer.build_index` **du moteur lui-même** (et non
     du SQL maison) pour garantir un index conforme (tokenizer, `rowid = unit_id`) ;
  3. résultat : **46 674 unités indexées en 0,4 s**, exactement le compte des unités `line` ;
     `fts_units` recréée, `integrity_check: ok` ; recherches vérifiées
     (`MATCH bouche` → 59, `maison` → 191, `the` → 7 454).
  → Confirme le correctif : **une fois les fantômes purgés, le chemin de reconstruction existant
  fonctionne sans autre modification**. Le seul changement à faire dans `indexer.py` est de rendre
  cette purge inconditionnelle avant le `CREATE`.
  L'état pathologique reste reproductible pour le test RED (script minimal, scratchpad de session).

### QA-05 — un import peut produire un document 100 % `structure` : inexploitable et sans issue

- **Sévérité** : 🟢 **P2** — ré-évaluée à la baisse après arbitrage (2026-08-17). **Ce sont les
  documents qui sont en cause, pas le programme** : importés dans un mode « lignes numérotées » qui
  ne leur convenait pas, remède = ré-import. Ces 4 fichiers sont connus comme inutilisables et ne
  demandent aucune récupération. **Hors périmètre du lot de juillet.**
- **Ce qui reste néanmoins imputable au code, et rien de plus** : la garde IMP-02, ajoutée en
  juillet pour empêcher les « documents fantômes », exige ≥ 1 **unité** et non ≥ 1 unité
  **exploitable** → un document vide pour toutes les capacités la franchit. Écart entre l'intention
  du correctif et son effet. Le constat détaillé ci-dessous vaut comme **cas d'espèce documenté**,
  pas comme demande de chantier.
- **Constat** : 4 documents — **408 `Swift-Light-AL_EN`**, **409 `Swift-Light-AL_FR`**,
  **417 `Coe-House-AL_FR`**, **418 `Coe-House-AL_EN`** — contiennent **une seule unité**, de type
  `structure`, portant **tout le texte** (67 747 à 77 778 caractères) et **zéro ligne**.
  Comparaison : doc 416 = 1 231 unités pour 94 011 caractères.
  Ce sont **deux paires source↔traduction complètes** (Swift EN/FR, Coe FR/EN), visiblement
  destinées à l'alignement (dossier `GRAFE-Lit-EnFr-Aligné-DOCX`, suffixe `-AL`).
- **Pourquoi c'est une impasse** — aucune capacité ne s'applique et aucune ne peut les rattraper :
  - **non indexés** (FTS ne prend que les `line`) → invisibles à la recherche ;
  - **non alignables**, **non annotables** (les deux travaillent sur des lignes) ;
  - **stylo refusé** : la garde `isLine` exclut les unités `structure` (comportement voulu) ;
  - **segmenteur inopérant** : `segmenter.py` ne lit et n'écrit que `unit_type = 'line'`
    (lignes 330, 417, 423, 492-498) → il n'a **rien à segmenter** et ne peut pas convertir le bloc.
  → Seule sortie : **ré-importer** dans le bon mode.
- **✅ Le moteur gère ce cas explicitement — correction d'une affirmation antérieure de cette fiche**
  (qui disait « rien ne le signale »). `POST /segment/preview` sur le doc 417 répond :
  ```
  Document doc_id=417 has no segmentable line units. Document has 1 non-line unit(s) —
  likely a failed import (text stored as a single 'structure' block). Re-import is required.
  ```
  Le message **nomme la cause et le remède**. L'utilisateur qui tente de segmenter est donc
  correctement informé. (Vérifié par appel réel au sidecar ; sur le doc 416 le même aperçu rend
  `units_input: 1231 → units_output: 1263`, sans avertissement.)
- **Cause exacte, établie par exécution à blanc des analyseurs sur les fichiers (2026-08-17)** :
  ces docx contiennent **tout le texte dans UN SEUL paragraphe Word**, lignes séparées par des
  `<w:br/>` (853 pour Coe, 1 211 pour Swift, 1 179 pour Beigbeder) — **aucun tableau, aucune
  colonne** ; c'est le format des bitextes GRAFE, identique pour les documents qui fonctionnent.
  `docx_numbered_lines` classe **paragraphe par paragraphe** via `_NUMBERED_RE` (`^\[\s*(\d+)\s*\]`)
  appliqué au **début du bloc** :
  ```
  doc 416 → '[4]\t Frédéric Beigbeder, 99 Francs, Editions Grasset…' → match → line
  doc 417 → 'Jonathan Coe, La maison du sommeil, traduit par…'       → pas de match → structure
  ```
  L'en-tête bibliographique du Beigbeder porte son marqueur `[4]`, celui du Coe non. **Rien d'autre
  ne les distingue.**
- **Conséquence généralisable (le vrai enseignement)** : le format « tout le texte dans un
  paragraphe » fait que la granularité de l'analyseur (un paragraphe = une unité) coïncide avec le
  **document entier**. La nature de 70 000 caractères se décide donc sur ses **premiers
  caractères** : une seule ligne d'en-tête non numérotée bascule tout le texte en `structure`, donc
  en inerte. Quand ça marche, c'est parce que la première ligne se trouve numérotée.
  → **Contrôle à faire avant tout import GRAFE en mode « lignes numérotées »** : vérifier que la
  première ligne porte son `[N]`.
- **Remède vérifié** (exécution à blanc) : ré-importer ces 4 fichiers en mode **`docx_paragraphs`**
  → 1 unité de type **`line`**, ensuite segmentable comme le 416 (dont les 1 231 unités viennent
  d'ailleurs de la **segmentation**, pas de l'import : l'import ne produit qu'un bloc unique).
  Aucun correctif moteur nécessaire.
- **Origine** : famille d'importeurs « lignes numérotées » (`docx_numbered_lines`,
  `odt_numbered_lines`, `txt`) — tout paragraphe ne correspondant pas au motif de numérotation
  attendu devient `unit_type="structure"`, non indexé (`docx_numbered_lines.py:107`,
  `txt.py:119`). Ces 4 fichiers ont été importés dans ce mode sans s'y prêter.
  **Provenance non traçable** : `documents.meta_json` est **vide** pour ces documents — le mode
  d'import n'est enregistré nulle part (à rapprocher de l'audit import du 2026-07-20).
- **Gap dans la garde IMP-02** : `insert_units` (`importers/parsed.py:52-62`) lève `ValueError`
  seulement quand la liste d'unités est **vide**. Un document composé uniquement d'unités **non
  indexables** franchit la garde tout en étant vide pour **toutes** les capacités. La garde compte
  des unités, pas des unités *exploitables*.
- **Correctifs possibles** (par coût croissant) :
  1. **durcir la garde à l'import** — exiger ≥ 1 unité `line`, ou avertir explicitement, en
     reprenant le message déjà écrit pour `/segment/preview` (il est bon, il arrive juste tard) ;
  2. **signaler dans la liste des documents** un document à 0 ligne — c'est le seul endroit où
     l'état reste invisible aujourd'hui, la segmentation, elle, le dit clairement ;
  3. ~~permettre au segmenteur de convertir une unité `structure` en lignes~~ — **écarté** : le
     moteur oriente déjà vers le ré-import, qui est la bonne réponse.
- **Test à ajouter** : import d'un docx ne correspondant pas au motif de numérotation → assertion
  sur le comportement retenu (rejet, ou avertissement + document marqué).

### QA-06 — « Pré-remplir » (Tours) : mutation de masse sans aperçu **ni annulation**

- **Sévérité** : 🟠 (peut écraser sans retour un travail manuel de structuration ; pas de perte de
  texte). Relevé par l'utilisateur en préparant l'item 4.4.
- **Constat** : sur la surface **Tours**, le bouton « Pré-remplir » applique le regroupement au
  **document entier** dès le clic. Aucun moyen de se projeter avant, aucun moyen de revenir après.
- **Vérifications** :
  - **pas d'aperçu** : `_prefillTours` (`SegmentPane.ts:913-938`) appelle `regroupCoarse`
    directement ; `POST /segment/coarse` n'accepte que `doc_id` / `preset` / `pattern` — aucun
    paramètre d'essai à blanc ;
  - **pas d'undo** : `regroup_document_coarse` (`coarse_grain.py:269`) n'a **pas** de paramètre
    `record_action`, et l'adaptateur (`sidecar.py:5496-5510`) ne lui en passe aucun. Aucun type
    d'action correspondant dans `PREP_ACTION_TYPES` (`prepUndo.ts:27-33`).
- **Asymétrie révélatrice** — dans la **même** surface :
  | Geste | Portée | Aperçu | Annulable |
  |---|---|---|---|
  | clic sur un n° ¶ (`/segment/paragraph_boundary`) | 1 segment | — | **oui** (Mode A, mig 034) |
  | « Pré-remplir » (`/segment/coarse`) | **tout le document** | **non** | **non** |
  Le geste minutieux est réversible, le geste massif ne l'est pas.
- **Portée du dommage** : non destructif au sens des données (seul `meta_json.parent_n` est
  réécrit ; texte, `alignment_links` et FTS intacts ; opération idempotente) — mais **la structure
  de paragraphes posée à la main est écrasée**, sans avertissement ni retour. C'est exactement le
  travail produit par les items 4.5/4.6.
- **Incohérence de couche** : *Phrases*, *Balises [N]* et *Personnalisé* fonctionnent toutes en
  « aperçu puis appliquer » (barre d'application dans la feuille). Tours est en « liste vivante »,
  ce qui se justifie pour le clic unitaire — mais le pré-remplissage a hérité de ce modèle alors
  qu'il s'agit d'une mutation de masse.
- **Confirmé sur pièce (2026-08-18)** : l'utilisateur a déclenché « Pré-remplir » sur le doc 416
  (base de travail). Résultat mesuré :

### QA-08 — le « % » du sélecteur de traduction n'est pas une ressemblance

- **Sévérité** : 🟠 (induit en erreur sur le geste central de la réparation d'alignement).
  Relevé par l'utilisateur au bloc 5.
- **Constat** : dans « = Rattacher une traduction », chaque candidat porte un pourcentage. Un
  segment **au texte identique** (structurel : « 2 ») est noté **25 %** tandis qu'un texte sans
  aucun rapport (« Yup, that's right, I pollute the universe. ») est à **100 %**.
- **Explication** : le score ne regarde **jamais le texte**. `build_retarget_candidates`
  (`services/align_links_service.py:193-250`) score par **proximité de marqueur `[N]`** :
  ```python
  if u_ext == pivot_ext_id:  score = 1.0              # même external_id
  elif dist <= window:       score = 1/(1 + dist)     # voisinage
  ```
  Les valeurs observées (100, 50, 50, 33, 33, 25, 25, 20, 20, 17) sont exactement `1/(1+Δ)` pour
  Δ = 0,1,1,2,2,3,3,4,4,5. C'est une **distance à l'ancre**, affichée comme un pourcentage.
- **Pourquoi c'est trompeur** : un « % » posé à côté d'un texte se lit comme une similarité —
  d'autant que la liste est faite pour *choisir la bonne traduction*. La nature réelle n'apparaît
  que dans l'infobulle (`reason` : « neighbor (Δ3) »), invisible tant qu'on ne survole pas.
- **Correctifs** :
  1. **étiqueter honnêtement** (front pur) : afficher « Δ3 » ou « voisin ±3 » plutôt qu'un %, ou
     accoler la raison au badge ;
  2. **ajouter un vrai signal textuel** (moteur) : `text_norm` est disponible des deux côtés ; un
     score lexical, ne serait-ce qu'en départage, ferait remonter en tête les segments identiques —
     cas fréquent et décisif pour les unités structurelles (numéros de chapitre, intertitres).
     À cadrer avec le fallback positionnel existant, conçu pour les corpus **sans** marqueurs.
- **Test à ajouter** : deux candidats dont l'un a un `text_norm` identique au pivot → il doit être
  proposé en tête (RED sur le code actuel).

### QA-09 — 🔴 le stylo de la matrice est inopérant : la grille affiche `text_raw`, le stylo écrit `text_norm`

- **Sévérité** : 🔴 — **fonctionnalité livrée en juillet (`f626c79`) sans effet visible aucun**.
  L'utilisateur corrige, le moteur enregistre correctement, la matrice réaffiche le texte d'origine.
  Aucune perte de données, mais la fonction est inutilisable et donne l'impression d'un logiciel
  qui ignore les saisies.
- **Repro** (constatée en aveugle par l'utilisateur, sur deux segments successifs) : matrice,
  famille Beigbeder → ✎ sur une cellule source → corriger → valider → **la cellule est inchangée**.
  Recommencer donne le même résultat.
- **Preuve directe** (payload réel de `POST /align/matrix`, doc 416 segment 200, unité 251524) :
  ```
  cellule affichée  : 'Il continue sa danse du ventre : —\tNous avons…'   → == text_raw   ✔
  text_norm en base : 'Il continue sa danse du ventre :—\tNous avons…'    → == cellule    ✘
  ```
- **Cause** : deux décisions justes séparément, incompatibles ensemble.
  - Le stylo édite **`text_norm`** et **préserve `text_raw`** — c'est l'invariant **D-C1**, voulu et
    vérifié par ailleurs (item 4.3 : `text_raw` intact = comportement correct) ;
  - `matrix_export_service` projette **`text_raw`** partout : lignes moyeu (l. 128 et 287),
    cellules de traduction (l. 171 → `target_text_raw`), orphelines (l. 209, 231).
  La note de conception affirme pourtant l'inverse : « sauvegarde → `_reloadPreservingScroll`
  (re-projection ; **la source corrigée réapparaît**) » (`DESIGN_inline_text_correction.md` §10).
  L'intention est claire, la projection lit l'autre colonne.
- **Pourquoi les tests ne l'ont pas vu** : les tests du lot vérifient que l'éditeur s'ouvre sur la
  bonne cellule et que l'appel part avec le bon `unit_id` — tout cela est exact. **Aucun ne compare
  ce que la grille réaffiche après sauvegarde.** C'est le même angle mort que QA-02 (rien ne teste
  le rendu final).
- **À trancher — ce n'est pas un simple remplacement de colonne** : la matrice affiche `text_raw`
  pour de bonnes raisons (balisage riche `<hi>`, fidélité au document source, tranches de coupe
  calculées en offsets sur `text_raw` — cf. `matrix_export_service` §6 « cut slices »
  `text_raw[cs:ce]`). Basculer sur `text_norm` casserait les offsets de coupe. Pistes :
  1. projeter `COALESCE`-style : `text_norm` **quand l'unité porte une correction**
     (`text_source`/flag d'édition), `text_raw` sinon — préserve les offsets pour les non-éditées ;
  2. transporter **les deux** dans le payload et laisser le front choisir l'affichage ;
  3. a minima **signaler** la divergence dans la cellule (pastille « corrigé ») pour que
     l'utilisateur sache que sa correction existe ailleurs.
- **Portée réelle, relevée par l'utilisateur — le plan affiché n'est pas le plan calculé** :
  l'**aligneur** travaille sur **`text_norm`** (`aligner.py:379, 1042, 1085, 1093`), tout comme la
  recherche (FTS) et la curation. La matrice, elle, affiche `text_raw`. Donc **vérifier
  visuellement un alignement dans la matrice, c'est juger sur une colonne que le système n'utilise
  pas**. Le défaut dépasse « ma correction est invisible » : c'est une divergence entre la surface
  de contrôle et la surface de calcul.
  *Atténuation* : pour une unité **non corrigée**, `text_raw` et `text_norm` ne diffèrent que par la
  normalisation (espaces, guillemets) — le sens est identique et le jugement d'appariement reste
  valable. La divergence n'induit en erreur que sur les unités effectivement éditées.
- **Vérifier aussi** : la couche Segment/Brut affiche-t-elle `text_raw` ou `text_norm` ? Le même
  piège peut s'y trouver (l'item 4.3 a validé l'écriture en base, pas le réaffichage).
- **Test à ajouter** : éditer une unité au stylo puis relire `POST /align/matrix` → la cellule doit
  refléter la correction (RED sur le code actuel).

### QA-10 — alignement « position » : la borne exclut le paratexte mais ne rebase pas la numérotation

- **Sévérité** : 🟠 (la stratégie ne fonctionne que si les deux documents ont **exactement** le même
  nombre de lignes de paratexte — condition jamais énoncée et rarement vraie).
- **Constat** : sur la paire 416/364, l'alignement positionnel apparie `n↔n` en absolu
  (5↔5, 200↔200, 1000↔1000). La **première phrase du texte anglais** (n=3) n'est appariée à rien :
  elle n'appartient à aucune paire possible.
- **Cause** (`aligner.py:800-856`) :
  ```python
  pivot_pos  = {n: uid}          # filtré n >= text_start_n   → paratexte bien exclu
  target_pos = {n: uid}          # filtré n >= text_start_n   → idem
  common = sorted(pivot_ns & target_ns)   # ← intersection des n ABSOLUS
  ```
  La borne sert à **exclure** le paratexte, jamais à **rebaser** la numérotation. Corps FR = n 4→1231,
  corps EN = n 3→1269 : l'intersection démarre à 4, et le n=3 anglais est structurellement perdu.
- **Cas réel mesuré** : le français porte 3 lignes de paratexte, l'anglais 2 ; de plus le numéro de
  chapitre (« 1. » / « 1 ») est **côté texte** en français et **côté paratexte** en anglais. Décalage
  de 2 dès la première ligne, puis dérive variable (vérifié aux segments 300, 800, 1200 : aucun des
  décalages −2/−1/0 ne correspond).
- **Ce n'est pas une violation de spec, c'est une ADR périmée** : ADR-013 (2026-02-28) décide
  « alignment by shared sequential position `n` » — **avant** l'existence du modèle de paratexte
  (borne `text_start_n`, R4.1 / migration 023). Les deux fonctionnalités n'ont jamais été
  réconciliées. La borne crée précisément la situation que l'appariement en absolu ne sait pas gérer.
- **Correctif** : apparier par **rang dans le corps** (le i-ème segment de corps de la source ↔ le
  i-ème de la cible) au lieu de l'intersection des `n`. Petit changement, effet majeur : il annule
  d'un coup tout décalage constant de paratexte. À faire avec une mise à jour d'ADR-013 et un test
  sur documents à paratextes asymétriques.
- **Conséquence produit (la vraie question posée par l'utilisateur)** : aujourd'hui, un corpus dont
  les deux versions n'ont pas le même nombre de lignes d'en-tête **ne peut pas** être aligné
  correctement par position, et rien dans l'interface ne l'explique. L'utilisateur voit une
  couverture de 100 % entièrement fausse — pire qu'un échec visible.
- **Test à ajouter** : deux documents à paratextes de tailles différentes → le premier segment de
  corps de l'un doit s'apparier au premier segment de corps de l'autre (RED sur le code actuel).

### QA-13 — le panneau Diagnostic sonde le sidecar par un `fetch` direct, que le navigateur bloque : il affiche « Running : no » pendant que l'application dialogue avec lui

- **Sévérité** : 🟠 (l'outil qu'on ouvre *quand quelque chose ne va pas* se trompe sur le seul fait
  qui compte, et se trompe dans le sens le plus déroutant).
- **Déclencheur observé (2026-08-19, item 8.1)** : ouverture de la modale Diagnostic
  (`shell.ts:1744` → `diagnostics.ts:186`). Console :
  ```
  Access to fetch at 'http://127.0.0.1:59671/health' from origin 'http://localhost:1422'
  has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
  GET http://127.0.0.1:59671/health net::ERR_FAILED 200 (OK)
  ```
  Le `200 (OK)` accolé à `ERR_FAILED` dit tout : **le sidecar a répondu**, c'est le navigateur qui
  a jeté la réponse.
- **Les deux lignes qui l'encadrent prouvent que le sidecar va bien.** À la même seconde,
  `sidecarCore.ts:81` journalise un `/health` **réussi** — parce que celui-là passe par la commande
  Rust `sidecar_fetch_loopback` (`main.rs:24`), qui sort du webview et n'est donc pas soumise à la
  politique d'origine. Le commentaire de `sidecarCore.ts:223` le dit mot pour mot : *« bypasses
  plugin-http scope entirely »*.
- **Le défaut est une exception unique à une règle par ailleurs tenue.** Inventaire de tous les
  `fetch()` littéraux vers le sidecar dans les trois fronts (hors tests) :

  | site | voie |
  |---|---|
  | tout `tauri-prep`, tout `tauri-app`, `shell.ts`, `rechercheModule.ts` | `sidecarFetch` → commande Rust |
  | **`diagnostics.ts:99`** | **`fetch()` brut depuis le webview** |

  `diagnostics.ts` ne mentionne `sidecarClient` que **dans deux commentaires** ; il ne l'importe
  jamais. C'est le seul module du shell qui reparle au sidecar en direct.
- **Le sidecar n'émet aucun en-tête CORS, et c'est cohérent** — vérifié en direct sur le port
  59671 : `HTTP/1.0 200 OK`, `Content-Type: application/json`, `Content-Length: 237`, et **rien**
  d'autre. Aucune occurrence de `Access-Control-` dans `sidecar.py`. Puisque tout passe par le pont
  Rust, la question ne s'est jamais posée. Le correctif n'est donc **pas** d'ajouter du CORS au
  moteur — ce serait ouvrir la boucle locale à toute page chargée dans le webview — mais de faire
  passer la sonde par le même pont que le reste.
- **Ce que l'utilisateur voit** : le `catch` de `_probeSidecar` (`diagnostics.ts:115`) renvoie
  `{ running: false, error: … }`, et le rapport imprime `Running : no` (`diagnostics.ts:274`).
  La branche `running` étant fausse, **Host/Port et Token required disparaissent aussi** du rapport
  (ligne 275). Le panneau de diagnostic est donc muet sur l'hôte, le port, et l'exigence de jeton —
  exactement les trois champs qu'on irait y chercher. Et si l'utilisateur colle ce rapport dans un
  signalement, il transmet une information fausse.
- **Ce n'est pas un artefact du mode dev.** L'origine change en application installée
  (`tauri://localhost`), mais une requête vers `http://127.0.0.1:<port>` y reste **cross-origin** et
  bute sur la même absence d'en-tête. Le mode dev ne fait que rendre le message plus lisible.
- **Correctif** : remplacer le `fetch` de `_probeSidecar` par `sidecarFetch("/health")` (ou par un
  appel direct à `invoke("sidecar_fetch_loopback", …)` si l'on veut garder `diagnostics.ts` sans
  dépendance). Deux effets secondaires bienvenus : la sonde cesse de dépendre du port recopié dans
  `localStorage` (`shared/sidecarCore.ts:306`) — donc de sa fraîcheur — et le rapport regagne les
  versions moteur/contrat que `_probeSidecar` sait déjà lire (`diagnostics.ts:107-114`) mais n'a
  jamais pu remonter. **Recoupe S-02** : ce panneau est précisément la surface que S-02
  propose d'étoffer pour l'application installée — autant qu'il dise vrai d'abord.
- **Test à ajouter** : `_probeSidecar` avec `invoke` moqué ⇒ `running: true` et champs de version
  peuplés ; garde de non-régression interdisant un `fetch()` littéral vers `127.0.0.1` dans
  `tauri-shell/src` (grep en test, sur le modèle des gardes de nommage CSS).

### QA-14 — le tiroir Journal se ferme en masquant aux lecteurs d'écran l'élément qui a le focus

- **Sévérité** : 🟢 (avertissement Chromium, aucun effet fonctionnel ; défaut d'accessibilité réel
  mais transitoire).
- **Déclencheur observé (2026-08-19, item 8.1)** : fermeture du Journal par son bouton ✕.
  ```
  Blocked aria-hidden on an element because its descendant retained focus.
  Element with focus:   <button class="prep-journal-close-btn" id="prep-journal-close">
  Ancestor with aria-hidden: <div class="prep-journal-drawer" aria-hidden="true">
  ```
- **Mécanique** (`app.ts:296` et `489-503`) : le clic sur ✕ appelle `_toggleJournal`, qui pose
  `aria-hidden="true"` sur le tiroir. Le bouton cliqué — descendant de ce tiroir — a encore le
  focus à cet instant. Chromium avertit avant que le `visibility: hidden` du CSS (`app.css:70`)
  n'ait retiré le bouton du parcours de focus : la contradiction est réelle, même brève.
- **Ce qui manque est aussi le comportement attendu** : à la fermeture d'un panneau, le focus doit
  **revenir au déclencheur**. `_toggleJournal` tient déjà la référence utile — `btn`, le
  `#prep-journal-btn` de la barre supérieure, qu'il ne touche que pour basculer sa classe `active`
  (ligne 502). Un `btn?.focus()` **avant** la pose de `aria-hidden`, quand on ferme, corrige à la
  fois l'avertissement et la navigation clavier : sans lui, le focus retombe sur `<body>` et la
  tabulation suivante repart du début de la page.
- **Alternative citée par la spécification elle-même** (et par le message de Chromium) : `inert`
  sur le tiroir fermé, qui interdit le focus au lieu de le masquer. Plus robuste, mais ne dispense
  pas de rendre le focus au déclencheur.
- **Correctif** : dans `_toggleJournal`, sur la branche fermeture, `btn?.focus()` puis
  `aria-hidden`. Trois lignes.
- **Test à ajouter** : ouvrir puis fermer le tiroir par son ✕ ⇒ `document.activeElement` est
  `#prep-journal-btn`, et aucun descendant de `[aria-hidden="true"]` n'a le focus.

### S-03 — propager une correction d'alignement au lieu de la refaire segment par segment

- **Demande (utilisateur, bloc 5)** : « une fois que j'ai aligné un 1er segment, on ne peut pas
  avoir la suite qui se propage ? » — **non**, aujourd'hui.
- **État actuel** : `/align` (`sidecar.py:6532`) n'accepte que `pivot_doc_id` + `target_doc_ids` :
  il aligne un couple de documents **en entier**, sans point de départ, sans plage, sans reprise.
  La réparation manuelle se fait donc segment par segment, sans fin.
- **Pourquoi ça fait mal ici** : `build_retarget_candidates` ancre chaque pivot sur **son propre
  lien courant** (`anchor_ext_id = current_link[1] if current_link else pivot_ext_id`). Quand la
  dérive est un **décalage constant** — cas typique lorsque les granularités de segmentation
  source↔traduction diffèrent —, corriger le segment 33 n'apprend rien au segment 34, qui continue
  de proposer ses candidats autour de son ancre fausse. L'utilisateur refait N fois la même
  correction.
- **Piste** : après un ré-ancrage manuel, offrir « **décaler la suite de Δ** » (Δ = écart entre
  l'ancienne et la nouvelle cible), applicable jusqu'au prochain lien validé ou jusqu'à la fin de
  la section. Le calcul de Δ est trivial ; le geste est une mutation de masse → prévoir aperçu
  **et** undo (leçon de QA-06).
- **Rapproche de** : l'insight de la refonte de l'espace Alignement — la dérive vient d'une
  granularité différente, irréparable à la source, donc corrigée à la main dans la matrice. Cette
  suggestion vise à rendre cette correction manuelle **tractable**.
- **Statut** : consigné, non fait. À cadrer avec `DESIGN_alignment_workspace.md`.

### S-04 — les exports ne portent aucune référence, et le TEI lit le mauvais stock de métadonnées

- **Demande (utilisateur, 2026-08-18)** : « les exports doivent contenir les références
  (métadonnées) ». En la vérifiant, deux problèmes distincts sont apparus, dont le second est un
  défaut, pas une amélioration.

**(A) Exports plats : aucune métadonnée du tout.**
`matrix_export_service.py:245` : `headers = ["paragraphe", "segment", hub_lang, *langs]`. Un CSV/TSV
exporté est donc **anonyme** — ni auteur, ni œuvre, ni édition, ni traducteur, ni date. Le fichier
n'est ni citable ni traçable une fois sorti de l'application, alors que le corpus stocke précisément
ces champs. Même constat à prévoir pour `align_csv`, `bilingual`, `csv_export`, `jsonl`, `html`,
`readable_text`.

**(B) TEI : les emplacements existent, mais il lit `meta_json` alors que l'application écrit dans des
colonnes dédiées.**
`exporters/tei.py:179-241` remplit `titleStmt` / `publicationStmt` depuis `meta.get("author")`,
`meta.get("publisher")`, `meta.get("pubPlace")`… c'est-à-dire **`meta_json`**. Or le modèle de
métadonnées R6.1/R6.3 a introduit des **colonnes** : `author_lastname`, `author_firstname`,
`work_title`, `publisher`, `pub_place`, `doc_date`, `translator_lastname`, `translator_firstname`.
**Aucun exporteur ne lit ces colonnes** (elles ne sont lues que par `metadata.py`, `query.py`,
`documents_service.py`, `sidecar.py`).
**Mesuré sur la base de QA** : **3 documents sur 54** portent des métadonnées en colonnes avec un
`meta_json` **vide** — leur export TEI émettrait un avertissement `tei_missing_field` pour chaque
champ, alors que la donnée existe en base. Ce qui est saisi dans l'écran Métadonnées **ne parvient
pas** à l'export.

- **Correctifs** :
  1. **(B) d'abord, c'est un bug** : faire lire aux exporteurs les colonnes dédiées (avec repli sur
     `meta_json` pour les corpus anciens), ou mirroir explicite à l'écriture. Sans quoi tout le
     travail de saisie de métadonnées reste invisible à la sortie.
  2. **(A) ensuite** : loger les références **dans le fichier d'export lui-même**.
     **Décision utilisateur (2026-08-19) : pas de fichier compagnon** — un fichier annexe se sépare
     de sa donnée à la première copie. (Ma recommandation initiale, écartée.)
     **Contrainte de forme qui en découle** : dans la matrice, les métadonnées sont **par colonne**
     (chaque colonne de langue est un document distinct : traducteur, éditeur, date propres ; seuls
     l'auteur et l'œuvre sont partagés). Des colonnes répétées à chaque ligne exigeraient donc un
     préfixe par langue (`en_traducteur`, `es_editeur`…) et gonfleraient le tableau.
     → **Forme retenue à cadrer : un préambule** de lignes clé/valeur avant la ligne d'en-têtes,
     décrivant le corpus puis chaque document/colonne. Préfixer ces lignes de `#` les rend
     ignorables par les parseurs courants (`pandas.read_csv(comment='#')`,
     `read.csv(comment.char='#')`) tout en restant **visibles à l'ouverture dans Excel** — ce qui
     est ici un avantage : la référence s'affiche en tête du document.
     Y porter aussi ce qui rend l'export **reproductible** : version d'AGRAFES, date d'export,
     stratégie d'alignement employée, nombre de liens.
     **Coût technique faible** : l'écriture passe par `_csv.writer` (`sidecar.py`, handler
     `_handle_export_matrix`) — un préambule est quelques `writerow` avant l'en-tête ; le payload
     de `/align/matrix` n'est pas concerné. À trancher : préambule systématique ou option.
     Garder **une seule convention** pour tous les exports plats (matrice, `align_csv`, `bilingual`)
     plutôt que d'optimiser chaque format séparément.
- **Statut** : consigné, non fait.
